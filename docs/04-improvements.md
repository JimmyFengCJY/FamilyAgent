# 优化前后对比与收益记录

本文件解释每轮优化解决了什么问题，与 PROGRESS.md 的实现/验证进度配套。历史记录依据已有进度与代码补录，不补造历史运行结果。所有例子均为合成说明；除明确标注的真实验证外，不代表真实模型输出或用户数据。

## 记录约定

每次优化追加：日期与里程碑、原有问题、改前/改后、具体例子、用户收益、工程收益、证据、代价/限制及待验证指标。尚未实现的内容只列在待办中。

“行为已验证”与“效果预期”分开：测试通过证明规定流程，不自动证明答案更好、延迟更低、费用更少。性能与质量收益须注明对照策略、案例、模型、样本量及测量条件；没有测量就不填写提升百分比。

## R0：模型适配与配置生效修复

日期：截至 2026-10-24，历史汇总补录。

| 方面 | 优化前 | 优化后 | 好处 |
| --- | --- | --- | --- |
| 供应商接入 | 首版以演示与 Claude 接入为主 | Claude / DeepSeek / Gemini 共用模型边界、结构化结果与用量记录 | 切换供应商时复用业务流程，便于后续对照 |
| 配置加载 | 启动脚本不自动读 .env，端口存在就可能复用旧进程 | 安全加载 .env，核对供应商/模型，R1 进一步核对代码与构建指纹 | 减少“改了配置但请求仍用旧值”的排查歧义 |
| 错误判断 | 通用 404 无法明确区分配置、权限或模型可用性 | 分类脱敏错误，通过实际适配器验证生成，再核对运行进程 | 不再把模型列表成功当作真实生成成功 |

**例子**：用户在 .env 修改 GEMINI_MODEL，但终端残留 FAMILYAGENT_MODEL，或 8000 端口仍是旧进程。以前新配置可能被覆盖或未加载；现在加载时处理已知覆盖情形，复用服务前核对实际模型配置，不一致时要求处理旧进程。

**收益与证据**：Gemini 的一个账号可用模型完成最小结构化生成，运行时配置核对后用户确认网页可用。当时后端 70 项测试通过。Claude / DeepSeek 是适配与模拟协议验证，不补称已用真实密钥验证。

**代价与限制**：模型可用性仍取决于账号与上游；历史可用模型不作为永久推荐。尚无真实多供应商质量/成本排名。

## R1：意图路由，会议结论与任务授权分离

日期：2026-10-24。

| 方面 | 优化前 | 优化后 | 好处 |
| --- | --- | --- | --- |
| 普通问答/倾听 | 回复倾向附带行动项，并触发任务确认 | 按消息意图处理，后端过滤不应出现的任务候选 | 用户可以只问问题或倾诉，无需处理不相关任务 |
| 建议转任务 | 有行动项就容易进入任务流程 | 建议先展示，用户主动整理草案，再确认写入 | 建议与执行授权区分清楚 |
| 家庭确认 | 成员同意结论会同时为发起人创建任务 | 先确认讨论结论；任务另行预览并由接收人确认 | 同意观点不再被当成接受待办 |
| 路由 | 会议问答也可能走完整专家链路 | 明确问答/倾听只由主持人回复 | 在规定场景减少不必要调用；不据此承诺实际金额或延迟 |

**例子一**：在个人规划空间问“什么是 SMART 目标？”以前可能附任务并要求确认；现在按问答解释，不生成任务草案。空间类型不自动代表任务授权。

**例子二**：家人同意“周末安排轻松行程”，只表示确认讨论结论。发起人还需选择“整理为任务草案”，预览“比较交通方案”等候选后再次确认，才创建自己的待办；不能替其他成员承诺任务。

**收益与证据**：95 项后端测试、桌面/手机演示回归通过。覆盖模型强行返回行动时的过滤、两阶段确认、权限与重复确认去重。固定完整三专家会议通常 5 次调用；明确问答路径为 1 次，这属于流程数量差异，未测真实费用收益。

**代价与限制**：意图使用保守中文规则，可能误判，可手动覆盖；任务暂不支持逐项编辑与转派。该轮没有新的真实 API 验证，不能宣称真实交互满意度已提高。

## R2 准备：配对评测与人工评审材料

日期：2026-10-25；真实质量基线仍待完成。

| 方面 | 优化前 | 优化后 | 好处 |
| --- | --- | --- | --- |
| 策略比较 | 主要看场景/策略分组汇总 | 同案例、同重复轮次配对，展示调用、耗时和 Token 差 | 更容易定位某个案例的资源代价，减少不同样本混比 |
| 人工评分 | 需在结果与调用 JSON 文件间寻找问题和标准 | review.md 集中展示问题、约束、标准与各阶段结果 | 降低评审整理成本，依据更容易核对 |
| 未评/失败处理 | 已区分未评分，但缺少配对约束 | 仅双侧完整评分才算分差，失败/缺失配对不计算差值 | 避免把缺失评分当零，或把不完整实验当改进证据 |
| 对标方向 | 缺少持续参考入口 | 将 Waku Agent 纳入对标文档，注明源码入口和边界 | 后续围绕能力差距推进，避免只堆功能名 |

**例子**：同一旅行案例，单助手 1 次调用、顺序专家 5 次调用。现在报告展示 +4 次调用；若只评了单助手，质量差显示“未完成双侧评分”，不会将另一策略按零分计算。两侧都完整评分后才显示分差。

**收益与证据**：95 项测试及 20 案例、26 次离线运行通过；没有人工评分。review.md 公开策略，不是盲评。尚未实际测量人工评审节省多少时间。

**代价与限制**：评审仍需人投入时间；单/多 Agent 总计算量不等。用户选择只做离线优化，真实模型质量、成本和延迟结论仍待验证。

## R3：专家首轮独立分析与可追溯分歧

日期：2026-10-25。

| 方面 | 优化前 | 优化后 | 好处 |
| --- | --- | --- | --- |
| 专家输入 | 后续专家看到本轮前序观点 | independent 策略同时隔离本轮结果与消息历史中的 Agent 发言 | 从输入机制上减少本轮互相影响；是否提高观点多样性待真实评测 |
| 汇总表达 | 以文字总结、建议与缺失信息为主 | 增加共同建议、分歧议题、引用与澄清问题 | 用户能直接查看待取舍事项及发言出处 |
| 分歧归属 | 缺少结构化引用约束 | 校验至少两个不同专家来源及逐字原文；非法引用有限重试 | 阻止不存在或错引的来源进入有效结果 |
| 对照能力 | 单助手与顺序专家 | 保留旧策略，新增独立策略；三策略离线比较 | 后续可比较机制变化，而非覆盖掉旧基线 |
| 恢复 | 有步骤检查点 | 恢复后继续维持独立上下文边界 | 不因暂停/恢复而读到本轮已完成专家发言 |

**例子一：独立分析**。输入“安排家庭旅行，预算 8000 元，兼顾老人休息”。以前规划师先建议紧凑行程，后续专家可能受其影响；现在预算与体验角色首轮看不到该建议，可以从各自职责独立分析。这里描述机制及潜在收益，不声称真实模型一定会提出不同意见。先前轮次讨论仍可见，独立不等于清空全部历史。

**例子二：分歧可追溯**。假设规划师原文是“每天安排三个景点”，体验角色原文是“每天最多安排一个主要活动”。主持人可以引用两段原文，并问“活动数量还是休息时间优先？”若引用不存在的专家或编造原文，后端拒绝并按预算有限重试。这是合成说明；两段话有引用不代表冲突判断或现实建议正确。

**收益与证据**：104 项后端测试、构建和桌面/手机浏览器回归通过；20 案例、32 次运行、80 次演示调用通过工程检查。测试验证输入隔离、恢复、引用校验及单专家不造双边分歧；8011 离线预览完成运行时核对与合成流程。

**代价与限制**：专家仍串行，完整三专家流程仍通常 5 次调用；独立与顺序策略输入内容不同，尚无真实 Token/成本收益结论。分歧格式错误可能产生一次额外格式重试。暂无自动第二轮、并行、动态选专家或标准 A2A 服务；真实答案质量及用户体验仍未验收。

## R4：上下文预算与持续约束（2026-10-25）

| 方面 | 改前 | 改后 | 好处 |
| --- | --- | --- | --- |
| 早期关键要求 | 依赖最近 10 条消息，较早要求可能退出窗口 | 新建空间可手动保存最多 8 条持续约束，每次运行快照保留 | 用户明确保存的要求不随历史窗口消失；不代表 AI 必然遵守 |
| 输入大小 | 每条历史截断，但专家与工具结果累积缺少统一上限 | 系统提示和上下文 JSON 合计 32000 字符；按顺序移除旧历史、记忆、前序结果 | 输入规模有可核对上限；不宣称等同于模型 Token 窗口 |
| 关键内容放不下 | 可能直接提交大输入 | 当前问题、约束、角色、工具/财务结果和专家来源不裁剪；仍超限则调用前拒绝 | 避免静默删掉关键事实或伪造摘要，明确提示拆分讨论 |
| 裁剪可见性 | 难以解释哪些内容未进入输入 | 轨迹记录前后字符数、各部分移除数量、约束数量和 Token 粗估 | 便于排查模型遗忘与输入增长；事件不重复保存约束正文 |
| 恢复与复现 | 没有上下文策略快照 | 每次运行保存策略版本、预算和持续约束 | 后续继续运行时使用该运行的约束与预算，而非静默读新值 |

**例子**：新建旅行空间时填写“预算不超过 8000 元”“周日必须返程”。以前如果只在早期消息里说过，长对话后这些要求可能退出窗口；现在显式约束持续加入输入。系统不会自动从旧消息提取这两条，已有空间也不会自动补录。

**超限例子**：大量旧消息占满输入时，优先移除旧历史；约束、当前问题和工具真实结果保持原文。如果这些关键内容本身已超过预算，系统显示“关键上下文超过输入字符预算，未调用模型”，不会为凑预算静默裁剪引用，也不消耗一次调用次数。

**验证证据**：本轮完整后端 111 项通过；新增覆盖长历史下约束保留、快照、引用与工具结果不变、精确字符边界、输入不被原地修改、超限零调用与 API 字段边界。评测新增预算工程检查，20 案例、32 次运行、80 次演示调用全部通过；这不证明真实模型的约束满足率提高。

**代价与限制**：预算为字符上限，Token 使用 ceil(UTF-8 字节数/3) 粗估，不含供应商协议封装，实际 Token 仍以供应商 usage 为准。输入预算不控制累计费用。裁剪是确定性移除，不是语义摘要；可能丢失未显式保存的旧信息。先前的最近 10 条消息、每条 1600 字符和最近 6 条记忆限制仍保留，裁剪统计仅描述打包阶段的移除。没有自动提取、编辑持续约束、向量检索或真实质量对照。

**待验证收益**：真实长对话的约束遗漏率、质量变化、Token/延迟与成本收益，尚未测量，不填写提升比例。

R4 补充验证：桌面/手机浏览器通过约束填写、展示与预算轨迹检查；8011 预览运行时指纹核对通过，合成请求保留两条约束，输入 2124/32000 字符。此数字仅为一个离线示例，不代表平均输入规模或压缩收益。

## R5：授权记忆检索与输入来源（2026-10-25）

| 方面 | 改前 | 改后 | 好处 |
| --- | --- | --- | --- |
| 选取方式 | 开启记忆后取最近 6 条，不看本轮问题 | 先限定当前用户的私密记录，再按问题与持续约束做中文双字片段/英文单词匹配，按匹配词及文档频率排序，最多 6 条；无匹配不注入 | 可以找回较早的相关记录，减少固定注入新但无关的内容 |
| 权限位置 | 读取通用记录后在 Python 按用户过滤 | SQL 按类型、所有者与私密范围先过滤；家庭会议、情绪支持、未开启场景不查询记忆 | 把授权边界放在排序之前，禁用场景不接触候选正文 |
| 预算裁剪 | 记忆按旧顺序移除 | 检索按高分到低分排列，预算不足先移除低分项 | 避免把最高匹配项优先删掉；语义相关性仍可能误判 |
| 来源展示 | 不知道回复输入用了哪些记录 | 每条 Agent 消息记录实际预算后输入的来源 ID/内容指纹，页面按当前权限解析内容、保存来源和时间 | 用户可核对哪些记忆确实送入调用；不把它标成回答实际引用 |
| 删除与变更 | 没有来源状态说明 | 来源不复制正文；读取时检查权限、是否存在及内容指纹 | 删除/变更后不继续在来源面板冒充原记录，后续检索也不读取已删除原记录 |

**例子一**：两个月前保存“英语口语每天早上练习二十分钟”，之后连续保存 7 条咖啡口味记录。以前新问“英语口语建议”时，最近六条可能全是咖啡；现在可匹配到旧的英语记录。若问“量子物理”，没有匹配时不硬塞咖啡偏好。

**例子二**：规划回复下方显示“本次输入参考记忆（1 条）”，展开可见“来源：用户主动保存”、保存时间与匹配分数。删除这条记忆后，来源变成“原记忆已删除或不可访问”，不继续展示旧正文。已经生成的回复可能复述过这条记忆，不会因此自动清除；这不是完整的派生数据删除系统。

**验证证据**：121 项后端测试通过；构建与桌面/手机浏览器回归通过，覆盖来源展开与删除后的刷新。20 案例、32 次运行、80 次离线演示调用通过；新增 9 个固定手工标注检索用例，来源集合完全匹配为最近六条 3/9、词面检索 9/9。合成集刻意覆盖旧策略缺陷，只证明这些用例的改进，不代表真实准确率或回答质量提升。测试另验证其他用户/错误范围不召回、禁用场景不查询、旧记录召回、英文规范化、预算优先保留高分及来源原文不复制存储。

**代价与限制**：这是本地词面检索，不是向量 RAG 或自动长期记忆；同义改写、跨语言和仅单个汉字的查询可能漏检，普通双字重叠也可能误召回。用户仍需手动开启与保存。暂无冲突合并、过期治理或自动记忆提取。扫描与来源逐条解析适合当前小规模，未做大数据性能验证。每次调用重查当前记录，运行只快照策略，不冻结记忆正文；删除前已进入历史回复的内容仍可能通过历史上下文出现。

**收益边界**：匹配分数仅用于排序，不是事实置信度。实际输入不等于回答逐条引用；记录被检索不等于事实仍然正确或适用。未调用真实模型，未测真实质量、Token/金额或延迟提升比例。

## R6：统一工具注册、Schema 与授权（2026-10-25）

| 方面 | 改前 | 改后 | 好处 |
| --- | --- | --- | --- |
| 工具扩展 | Harness 中硬编码 task.list 分支，预算与批量创建各自处理 | 三个工具共享注册表：名称、描述、输入 Schema、能力、入口与风险 | 后续增加工具可复用校验与执行边界，减少核心编排分支 |
| 模型可见能力 | 固定提示词说明待办工具 | 根据当前角色/空间生成工具目录并计入上下文预算；执行前再授权 | 降低请求不可用工具的机会，同时保留真正的服务端拒绝机制 |
| 参数控制 | 待办请求只有名称 | 支持 arguments，Schema 限制状态、数量、类型并拒绝未知字段 | 可按需求读取待办，参数不能用来切换用户或伪造审批 |
| 写工具 | 审批接口内直接循环创建 | 注册表复核接收人、入口、有效期、草案哈希、已保存审批状态和精确行动列表 | 写能力迁入统一边界仍不能绕过人工确认 |
| 可观察性 | 工具事件分散 | 本地运行统一记录开始、完成、入口、风险、数量与耗时；模型非法请求明确拒绝 | 更方便定位工具执行及权限问题，不在事件中回显完整参数或内部异常 |

**例子一（工具请求示意）**：模型输出 `{"tool_request":{"name":"task.list","arguments":{"status":"todo","limit":1}}}`，服务端只读取当前用户的一条未完成任务，不返回其他家庭成员待办。若参数额外带 `owner_id`，不会按该用户读取，而是拒绝未知字段。此闭环使用离线模拟模型测试，演示模式不保证自动理解自然语言并选择此工具。

**例子二（审批边界）**：模型即使输出 `task.create_batch` 并附上 `approved:true` 也会被拒绝。只有用户确认有效任务草案后，服务端入口才能执行，而且行动必须与已确认草案完全一致。会议结论确认仍不会创建任务。

**例子三（原子性）**：批量创建时假设第二条写入发生故障，第一条已插入的任务、审批标记和工具事件一起回滚，草案仍等待确认。故障注入测试已验证，不会留下半批任务；稳定 ID 与状态检查继续防止重复创建。

**用户收益**：网页能查看工具权限说明；选择何种角色和空间时，工具边界更清楚。待办读取可以筛选，不需要把全部个人待办交给模型。没有测量用户操作时间或真实输入费用收益。

**工程收益与限制**：统一的是本地工具合约，不代表已经接入 MCP、原生供应商 Function Calling 或标准 A2A。现有工具同步执行，暂无远程超时/取消、输出 Schema 或进程沙箱。非法参数直接停止本次运行，不自动让模型无限纠错。单次任务标题与写工具统一限制为 150 字；过长新模型输出按结构错误处理，旧草案若不符合新合约会拒绝，需要重新整理。

**验证**：见 PROGRESS.md 的 R6 测试与运行记录；自动测试证明权限、事务和协议行为，不代表真实模型的工具选择准确率已提高。

## R8：事务外只读工具等待、检查点与执行代次（2026-10-25）

| 方面 | 改前 | 改后 | 好处 |
| --- | --- | --- | --- |
| 工具等待 | 模型工具在 SQLite 写事务内执行，包括 MCP 等待 | 短事务准备并存检查点，事务外执行，短事务复核后提交 | 工具阻塞期间，其他 API 写入与暂停/取消可以提交；不再被这一段写事务占住 |
| 旧响应识别 | 比较 running 状态和 worker ID | 同时比较每次 claim 新生成的 attempt_id、状态与有效租约 | 同一 Worker 暂停后恢复，也不会把旧响应误认成新执行 |
| 恢复粒度 | 模型已返回工具请求，但未存独立工具检查点 | 保存稳定逻辑工具 ID、校验后参数、步骤与状态 | 检查点提交后崩溃，可继续只读工具，无需重做已完成模型请求 |
| 提交授权 | 工具执行前授权 | 准备、执行入口及结果提交时复核；提交前重读身份和会话 | 等待期间权限变化后，不采纳已失效结果 |
| 迟到用量 | 被取消的模型响应直接丢弃，已报告用量可能漏记 | 内容丢弃，已报告 Token 按执行代次去重记入原运行与审计事件 | 更完整地解释已发生的资源消耗，不把取消误当免费 |

**例子一（并发屏障验证）**：让一个只读工具保持阻塞。在释放它之前，新建另一条待办和取消原运行都已提交。旧版写事务占着锁时，这些操作需要等工具结束；现在原工具返回后只记“旧执行结果已丢弃”，不写入工具结果或 Agent 消息。测试使用事件屏障验证顺序，不是测量真实网络延迟。

**例子二（同 Worker 旧响应）**：第一次工具执行被阻塞，用户暂停并恢复，由同一 Harness/Worker 接手。第二次执行提交 NEW_RESULT，再释放第一次 OLD_RESULT。验证结果只保留新的一份，逻辑工具请求次数仍为 1，模型请求次数仍为 1；这证明结果提交保护，不代表底层工具只执行了一次。

**例子三（崩溃恢复）**：模型请求已返回 task.list，检查点已提交，但尚未调用工具。模拟 Worker 退出与租约到期，新 Worker 从同一工具 ID 继续读取，不再请求模型。若崩溃早于该检查点提交，仍可能重做模型请求，此边界未消失。

**例子四（用量）**：旧模型响应被取消后迟到，报告 3 个输入 Token；新响应报告 2 个。只展示新回复，但运行总量保留 5 个输入 Token。该数值来自合成测试，不是实际供应商计费样本；缺失的 usage 仍不能按免费处理。

**工程收益**：执行路径明确分为准备、执行、复核提交；只读工具失败可以在用户明确恢复后重试检查点。本地审批写工具仍保留事务原子性，不能借事务外入口绕过审批。

**代价与限制**：引入执行代次、持久检查点和更多审计事件。默认嵌入 Worker 仍单线程，暂停/取消不保证立刻中断底层工具；只保证持久状态与迟到结果采纳边界。读工具可能重复物理执行，tool_requests 计逻辑请求，不能称 exactly-once。SQLite 仍单写者，未拆表、未建立数据库迁移、未做多 Worker 压测或租约心跳。

**验证**：本轮完整后端 165 项通过，其中新增 8 项执行并发/恢复测试；构建通过。更多浏览器、离线回归与实际预览证据见 PROGRESS.md。本轮没有真实模型调用，未测生产吞吐、平均延迟或金额收益，不填写性能提升比例。

| --- | --- | --- | --- |
| 核心存储 | run/message 与其他对象共享 records | 独立 runs、messages 表；其他对象暂留 records | 查询和约束可以围绕具体实体设计，减少通用 JSON 表承担的职责 |
| 核心字段 | 每次筛选从 JSON 表达式读取状态、会话与租约 | STORED 生成列加实体索引，状态/类型/ID 一致性由数据库检查 | 避免手动双写 JSON 和列产生偏差；无效状态、错误类型等写入会被拒绝 |
| 消息顺序 | 通用 records 的隐式 rowid | 实体表显式自增 seq，旧 rowid 原样迁入 | 原有消息 ID 游标仍定位相同顺序，更新正文不改变排序 |
| 迁移切换 | 只建版本历史和索引 | 复制、核对条数/顺序/原文，再移除旧记录，整体事务提交 | 不靠“新表存在”判断搬迁成功，失败可保留原有数据布局 |
| 旧写入与身份 | 通用记录缺少实体级保护 | 拒绝往 records 写 run/message；跨表 ID 防重，ID/会话/seq 不可改 | 避免旧写法静默产生第二份状态，存储归属更明确 |

**例子一（旧数据升级）**：v2 数据包含消息 seq=8、运行 seq=14、回复 seq=21，中间穿插其他任务。迁移后两张实体表保留这些顺序号、ID、JSON 原文；任务仍在原位置。使用旧消息 ID 向前翻页能读到原消息，再新增消息的顺序号大于旧尾部。事件从 50 接续到 51。

**例子二（恢复而非重跑）**：合成运行已完成一次模型调用并持久化 task.list 检查点，模拟旧 Worker 退出，再搬迁旧库。新 Worker 从原 call_id 继续工具读取，calls 和 tool_requests 仍各为 1，不再请求模型。该测试覆盖迁移与 Harness 恢复组合，未宣称外部调用 exactly-once。

**例子三（搬迁故障）**：迁移中故意改坏一条消息正文，逐行核对失败；另一个测试在删除旧行后注入非法 SQL。两者均整体回滚，旧正文/v2 版本和索引保留，不留下半迁移的新表。非法旧状态、ID 不一致、缺少会话或租约为字符串同样停止升级，不静默丢行。

**例子四（事务与并发）**：在同一事务写运行、消息、任务、事件后抛出异常，四类写入全部撤销；两 Worker 并发领取八条排队运行，八个运行 ID 与执行代次都唯一。这是小型正确性测试，不是吞吐或多机压力基准。

**验证中修正**：完整回归发现状态约束最初漏掉 waiting_user（真实成员拒绝草案后待重新讨论）。已补全现有九种状态，并新增从 v2 搬迁全部状态的测试。说明实体约束要依据所有状态转换点，不只依据 Worker 的执行分支；原有业务回归必须保留。

**验证证据**：完整后端 190 项通过（新增 12 项实体存储/搬迁测试）；构建与桌面/手机浏览器回归通过。32 次运行、80 次 demo 调用的离线检查通过。先在 8011 预览一致性备份上验证 v2→v3，确认 147 条运行/消息原文和顺序及其他记录/事件保留，再停服务备份并升级原临时预览；HTTP 核对指纹、旧分页、新运行完成及仅新表落盘。未打开默认业务库，未调用真实模型 API，未上传 GitHub。

**代价与限制**：新增索引、生成列和写入保护会增加写入/存储开销，迁移期间需要空间与停机窗口。复杂负载仍是 JSON，尚未达到完整关系规范化；会话仍在 records，未增加外键/级联删除或完整业务状态转换约束。旧进程不能混用，回退代码前需恢复旧备份。未做大型库迁移耗时、多进程故障压力、生产吞吐或成本测量，不编造性能提升比例。下一步优先租约续期与独立 Worker 故障验证。

## R12：有限心跳续租与独立 Worker 故障验证（2026-10-25）

| 方面 | 改前 | 改后 | 好处 |
| --- | --- | --- | --- |
| 长调用 | 固定 120 秒租期，调用未完成也可能过期 | 默认每 30 秒续租，每个执行代次最多延至领取后 600 秒 | 健康 Worker 持续工作时，可跨越初始租期；不让卡死调用无限续租 |
| 续租写入 | 没有独立续租路径 | 短连接、条件 UPDATE，只改租约相关字段 | 不用旧运行快照覆盖控制状态、步骤或用量；过期/换代后不能复活 |
| 故障证据 | 同进程并发与小型领取测试 | 实际子进程阻塞、竞争、强制结束、等待过期后接手 | 能展示进程级恢复证据，不把两个线程称为独立部署验证 |
| 工具恢复 | 已有持久检查点，未做进程强制结束试验 | 杀死工具进程后，其他 Worker 从原 call_id 恢复 | 已提交的模型工具请求不重做，逻辑调用计数保留 |
| 可观察性 | 能查看领取/回收和结果丢弃 | 增加 lease.renewed 事件、续租次数/时间与代次截止时间 | 可解释“为什么其他 Worker 没有接手”及续租边界 |

**例子一（健康长调用）**：离线模型停在文件屏障，持续超过测试初始 0.6 秒租期。数据库中观察到至少两次续租，另一个 Python 进程领取失败。强制杀死原进程后，等最后持久租约到期，第二进程接手并只发布一条 Agent 回复。证明的是这组进程/数据库条件下的行为，不是生产吞吐或可用性比例。

**例子二（检查点）**：模型已返回 task.list，calls=1、tool_requests=1；工具等待中强制结束进程。新进程读取原检查点并完成同一个 call_id，模型入口在恢复测试中被明确禁止。底层只读工具可能物理重做，不能称外部 exactly-once。

**例子三（有上限的续租）**：测试将窗口缩为 0.9 秒，旧模型仍阻塞。到期后新进程完成任务，再释放旧模型。结果只显示新回复，旧内容被丢弃，两个代次各报告的 1 个输入 Token 仍累计为 2。默认 600 秒来自代码配置，没有真实等待十分钟或调用付费模型。

**例子四（状态和锁）**：暂停、取消、更换 Worker/代次/期限、租约过期均不能续租；持有另一个 SQLite 写事务时，续租短等待失败。释放锁时租约已过期，依旧不能复活，避免把获得锁之前的旧时间当成当前时间。

**验证中修正**：严格截止测试发现 SQLite JSON 数字序列化会产生几微秒漂移；领取与续租的边界时间统一向下取毫秒精度后，再验证租期不超过截止时间。正式入口 smoke 使用显式交流意图，预期成功结束与待确认任务草案区分。

**验证证据**：完整后端 202 项通过（新增 12 项租约/子进程测试），构建、桌面/手机浏览器回归通过。生产 services.api.app.worker 入口在隔离 demo 库中完成一次合成运行并响应 SIGTERM 正常退出。20 案例、32 次运行、80 次 demo 调用离线评测通过。8011 指纹和新截止字段核对通过，快速合成请求完成，没有多余续租；实际续期与强制结束证据来自独立临时库测试，未把快速预览请求当成长任务验证。

**代价与限制**：每个活跃执行代次多一个心跳线程、周期写入和事件；SQLite 仍单写者。数据库持续繁忙、异常或时钟大幅变化仍会影响过期判定。截止上限和停止心跳不等于中断底层网络请求，超过窗口或结果提交前崩溃仍可能重复调用/计费。默认 Worker 仍串行，无多机压力测试、故障监控面板、生产 SLA 或已测成本收益。本轮不升级 schema、不打开默认业务库、不调用真实模型、不自动上传 GitHub。
